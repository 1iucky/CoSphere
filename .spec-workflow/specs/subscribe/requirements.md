# 需求规格文档: 订阅套餐扩展与计费优先级

**项目**: New API - AI网关与资产管理系统
**功能**: 扩展订阅套餐 / 优惠券 / 兑换 / 钱包优先级计费
**创建日期**: 2025-12-03
**最新修订**: 2025-12-03 (根据业务澄清更新)
**文档状态**: 草稿

---

## 1. 概述

### 1.1 背景
- 现有系统以余额(额度)计费为主,仅提供单一“包月”订阅逻辑,缺乏可配置的多周期限额、优惠/兑换玩法以及灵活的计费优先级。
- 管理员希望售卖多样化套餐(按月/按年/自定义周期),并允许通过优惠券、兑换码与钱包余额组合,满足 ToB 客户精细化运营需求。

### 1.2 目标
1. 支持管理员创建具备多时间周期限额、绑定模型/渠道分组的订阅套餐。
2. 订阅购买可使用优惠券或兑换码,并支持优惠券与兑换码绑定(第三方售卖场景)。
3. 用户端可查看订阅细节、计时/余量、历史流水及“自动余额兜底”开关。
4. 计费链路实现“订阅额度优先,余额兜底(可配置)”并能与令牌分组逻辑及订阅优先开关协同。
5. 兑换码支持发放订阅,可叠加时长或并行生效,并在账单中保留审计记录。
6. 订阅额度内部沿用当前 quota 计算,对用户展示时换算为 USD,并确保所有动作产生支付流水。

### 1.3 范围
- **在范围**: 数据模型升级、管理员/用户界面、API、订阅优先扣费、优惠券&兑换码改造、审计日志。
- **不在范围**: 自动退款、发票自动化(由线下处理)、套餐转让、跨租户共享、试用模板。

## 2. 功能需求

### 2.1 角色场景
| 角色 | 关键场景 |
|------|----------|
| 管理员/运营 | 配置套餐、绑定模型与渠道分组、生成优惠券/兑换码、人工取消订阅、导出账单 |
| 财务 | 审核支付流水、线下退款/开票 |
| 普通用户 | 购买/兑换订阅、查看余量、配置自动余额兜底、选择多订阅的使用顺序 |
| 计费服务 | 在请求流中决定扣费来源,记录日志/错误码 |

### 2.2 功能列表

#### FR-1 订阅套餐管理
- 字段: 名称/描述/封面、SKU 编号、定价(价格+币种)、计费周期类型(month, year, custom_days)、生效/停售时间、允许的钱包兜底策略默认值。
- **周期限额配置**:
  - 周期枚举: 5小时、自然日、自然周、自然月;
  - 周期采用**滚动窗口**: 当订阅首次使用或窗口刷新后第一次使用时记录 `window_start`,之后 `window_start + period_duration` 为 `window_end`; 窗口内累计使用值,到达限额或 `window_end` 时刷新下一窗口。
  - 每个周期可单独启用/禁用,可配置 quota 数值及单位(内部 quota 单位,展示换算 USD)。
- **模型与渠道**:
  - 支持绑定模型列表、渠道分组(沿用现有模型/分组定义); 若请求模型不在白名单或渠道分组不匹配,将跳过订阅扣费。
- 多语言描述 & 排序权重。

#### FR-2 优惠券改造

**核心目标**: 实现领取码发放、用户领券绑定、充值/订阅单笔单券核销、兑换码绑定专属用户+单券，并保持并发安全与审计完备。

##### FR-2.1 优惠券类型与范围
- **类型枚举** (`coupon.type`):
  - `discount`: 折扣（百分比，1-100）
  - `full_reduction`: 满减（需满足阈值）
  - `instant_reduction`: 立减
- **适用范围** (`coupon.scope`):
  - `wallet`: 余额充值（仅可用于钱包管理中的账户充值订单）
  - `subscription`: 订阅（仅可用于订阅支付订单）
  - `wallet_subscription`: 充值+订阅均可
- **订单类型判断规则**:
  - `wallet` 类型订单: 在**钱包管理**模块进行**账户充值**时产生的订单
  - `subscription` 类型订单: 在**订阅支付**流程中产生的订单（购买套餐、续费等）
  - 核销时根据订单来源模块自动判断订单类型，并校验优惠券 scope 是否匹配
- **币种**: 当前固定 CNY（人民币），未来可扩展多币种

##### FR-2.2 用户券状态管理
- **用户券状态** (`user_coupons.status`):
  - `available`: 可用
  - `locked`: 已锁定（核销进行中/兑换绑定）
  - `used`: 已核销
  - `expired`: 已过期
  - `invalid`: 作废
- **绑定表状态** (`coupon_redemption_bindings.status`):
  - `reserved`: 已绑定未锁定
  - `locked`: 已锁定（兑换时使用/已失效）

##### FR-2.3 领取与使用规则
- **单笔单券**: 单笔订单/充值仅可使用一张优惠券
- **领取限制**: 同一用户同一优惠券只能领取一次；同一用户可领取多张不同优惠券
- **领取流程**: 扣减库存 + 生成用户券实例，原子事务，乐观锁防止超发
- **核销流程**: 校验范围/时间/阈值/状态/归属，锁定并标记 `used`
- **满减阈值**: 基于"订单原价"（未扣券前的应付金额）判断
- **code 生成规则**:
  - 领取码格式: `COUPON` + `YYYYMMDD` + 6位随机大写字母数字（如 `COUPON20250109AB12CD`）
  - 用户券核销码格式: `UC-` + UUID

##### FR-2.4 兑换码绑定优惠券
- **绑定关系**: 支持将优惠券绑定到兑换码，用于第三方售卖
- **专属用户**: 兑换码可绑定专属 `user_id + coupon_id`，仅该用户可用
- **绑定状态**: 已锁定视为优惠失效，不可再次使用
- **绑定时机**:
  - 兑换前: 允许管理员修改或重新绑定
  - 兑换后: 绑定关系锁定，不可变更

##### FR-2.5 退款规则
- **核心原则**: 优惠券一旦核销（状态 `used`），**不可恢复**
- **退款金额**: 基于使用优惠券后的**实际支付金额**（`final_amount`）
- **退款操作**: 仅更新账单状态，不影响优惠券状态
- **退款类型**:
  - `manual`: 人工退款（管理员手动操作）
  - `auto`: 自动退款（系统自动触发）
  - `none`: 无退款（正常完成）

##### FR-2.6 并发安全
- **乐观锁机制**: 使用 `version` 字段防止并发超发
- **原子操作**: 库存扣减与领券插入同事务，依赖行锁/条件更新保证不超发
- **幂等性**: 核销使用条件更新防止重复使用，订单号+user_coupon_id 可作为幂等键

##### FR-2.7 审计与流水
- 优惠券/兑换码抵扣后生成支付流水 (`user_bills`) 并标记来源
- 记录完整的优惠券使用信息：`coupon_id`, `user_coupon_id`, `original_amount`, `discount_amount`, `final_amount`, `refund_type`
- 所有领券、核销、绑定、兑换操作写入 `audit_logs`

#### FR-3 用户端展示
- “我的订阅”显示:
  - 基础信息+状态(待生效/生效/即将到期/已过期/已取消)、开始/结束时间、剩余天数。
  - 每个周期的限额、已用、剩余、下次窗口刷新倒计时; 支持 USD 展示。
  - 支持模型/渠道列表,不支持的模型需提示。
  - 自动余额兜底开关(继承系统默认,用户可覆写); 详见 FR-4。
- 历史记录: 订单/优惠券/兑换码/手动取消日志。

#### FR-4 计费优先级与自动兜底
1. **订阅判定**: 在 `PreConsumeQuota` 前,根据用户所有生效订阅筛选当前模型/渠道可用的订阅,并按照“距离到期时间更近的优先”排序。订阅的渠道匹配以订阅自身绑定的分组为准,与 token 分组无关。
2. **扣费规则**:
   - 若订阅存在且 token.subscription_preferred=true，则尝试按周期顺序预扣订阅额度(滚动窗口)。
   - 若订阅额度充足 -> 标记本次来源为订阅。
   - 若额度不足:
     - `auto_wallet_fallback = true`: 自动走余额扣费;
     - `auto_wallet_fallback = false`: 返回错误 `SUBSCRIPTION_LIMIT_REACHED`。
   - 若令牌未启用订阅优先（subscription_preferred=false），则跳过订阅扣费,直接走余额并在响应中提示。
   - 令牌分组（含多分组优先级）仅作用于余额路径的转发选择,不参与订阅筛选。
3. **多订阅**: 若并存多个套餐,遍历优先级并可记录使用顺序; 默认按到期时间排序,并支持用户在“我的订阅”页面通过拖拽交互手动调整顺序,实时同步后端。

#### FR-5 兑换码支持
- 兑换码类型新增 `subscription`:
  - **同套餐 (`stack`)**: 直接延长当前订阅有效期(按套餐周期累加)并记录一条"兑换延长"流水。
  - **更贵套餐**: UI 提示用户选择:
    1. **并存 (`coexist`)**: 新套餐立即生效,旧套餐保留，两者独立计费。
    2. **折算 (`convert`)**: 将现有低价套餐按剩余天数折算成金额,再按新套餐日均价格换算为天数,并将新增天数**向下取整**后追加到兑换套餐有效期(不足一天金额记入流水)。操作完成后记录特殊流水标记。**注意**: 若折算不足新套餐 1 天的价格，不允许进行折算，报错提示用户端。
    3. **替换 (`replace`)**: 立即取消旧订阅，新套餐从当前时间开始生效，旧订阅剩余时间作废。
    4. **延期 (`extend`)**: 新套餐在旧套餐结束后开始生效，排队等待激活。
  - **不同模型/便宜套餐**: 默认并存,用户可在"使用顺序"里调整。
- **兑换选项枚举** (`redeem_option`):
  | 选项 | 说明 | 适用场景 |
  |------|------|----------|
  | `stack` | 叠加延长 | 同套餐兑换，直接累加有效期 |
  | `coexist` | 并存 | 不同套餐，两者同时生效独立计费 |
  | `convert` | 折算 | 旧套餐剩余价值折算为新套餐天数 |
  | `replace` | 替换 | 取消旧订阅，新套餐立即生效 |
  | `extend` | 延期 | 新套餐在旧套餐结束后排队生效 |

##### FR-5.1 兑换码绑定优惠券功能
- **绑定限制**:
  - 一个兑换码**仅能绑定一张优惠券**
  - 若兑换码绑定了优惠券，在兑换时自动抵扣并标记该优惠券为已使用
  - 每个兑换码仅能绑定一张优惠券，兑换前可修改或重新绑定，兑换成功后不可变更
- **专属用户校验**:
  - 兑换码可绑定专属用户 ID（`bound_user_id`）
  - 若 `bound_user_id` 不为空，仅该用户可使用此兑换码
  - 其他用户尝试使用将返回错误 `REDEMPTION_USER_MISMATCH`
- **绑定状态管理**:
  - 绑定记录状态（`coupon_redemption_bindings.status`）:
    - `reserved`: 已绑定未锁定，可以兑换
    - `locked`: 已锁定（兑换时使用或已失效），不可再兑换
  - 用户优惠券状态流转:
    - `available` → `locked`（兑换开始）→ `used`（兑换成功）
    - 若兑换失败，状态回滚为 `available`
- **兑换流程**:
  1. 校验兑换码有效性、未使用
  2. 查询 `coupon_redemption_bindings` 绑定记录
  3. 若绑定了专属用户，校验是否匹配当前用户
  4. 若绑定了优惠券，执行以下逻辑：
     - 锁定绑定记录：`status = 'reserved'` → `'locked'`
     - 检查用户是否已有该优惠券实例
       - 若无：创建 `user_coupons` 记录（`status = 'locked'`）
       - 若有：将状态从 `'available'` 改为 `'locked'`
  5. 执行兑换业务（充值/订阅）
  6. 兑换成功后，将用户优惠券状态改为 `'used'`
  7. 标记兑换码为已使用
  8. 写入审计日志

#### FR-6 令牌与模型限制
- 令牌管理保留“自动分组”开关（`auto_smart_group`），用于分组不可用时的自动回退/熔断。
- 新增“订阅优先计费”开关（`subscription_preferred`），控制是否进入订阅扣费逻辑:
  - 开启: 进入订阅扣费流程（订阅筛选与 token 分组无关）。
  - 关闭: 订阅扣费跳过,直接走余额/令牌分组规则。

#### FR-7 自动扣费开关
- 系统级配置提供默认值(可在设置中心配置)。
- 用户级设置可覆写系统默认,优先级: 用户设置 > 系统设置。
- 迁移时所有存量用户默认关闭(需通知提示),新用户继承系统配置。

#### FR-8 取消/退款与审计
- 系统不提供自动退款; 管理员可在订阅管理中执行"取消订阅"(立即失效,记录原因),并按系统配置与用户通知偏好推送提醒。
- **退款处理**:
  - 退款需线下处理,但系统必须支持写入一条人工退款流水
  - 若订单使用了优惠券，退款金额为**使用优惠券后的实际支付金额**（`final_amount`）
  - 优惠券**不恢复**，保持 `used` 状态
  - 退款流水需标记 `refund_type = manual`（人工退款）或 `auto`（自动退款）
  - 退款元数据需记录：`coupon_id`, `user_coupon_id`, `discount_amount`, `original_amount`, `refund_amount`, `coupon_restored = false`
- **退款场景分类**:
  - 支付成功后退款：退款金额 = `final_amount`，优惠券状态 = `used`（不恢复）
  - 支付失败回滚：无需退款，优惠券状态回滚为 `available`（事务回滚）
  - 订单取消（未支付）：无需退款，取消预扣，优惠券状态回滚为 `available`
- 所有支付/兑换/取消/自动兜底切换操作必须写入审计日志与 `user_bills`。
- 需保留可用于开票的基础信息,发票仍由线下处理。

#### FR-9 通知与错误提示
- 订阅即将到期、额度低于阈值时触发通知中心。
- 当令牌订阅优先关闭跳过订阅时,响应里需包含提示字段供前端展示。

## 3. 非功能需求
- **性能**: 订阅判定+预扣需 ≤5ms(缓存命中); 订阅 usage 更新需支持 2k QPS。

- **安全**: 管理员接口需权限校验; 用户仅能访问自身订阅; 所有金额相关 API 加幂等键。

## 6. 需求澄清与决策清单

本节记录所有关键业务决策和澄清事项，确保设计和实施的一致性。

### 6.1 兑换折算算法决策

**问题**: 当用户将现有低价套餐折算为更贵套餐时，如何计算剩余价值和新增天数？

**决策**:
- **折算公式**:
  ```
  剩余价值 = 旧套餐剩余天数 × 旧套餐日均价格
  新增天数 = floor(剩余价值 / 新套餐日均价格)
  剩余金额 = 剩余价值 - (新增天数 × 新套餐日均价格)
  ```
- **精度处理**: 新增天数采用**向下取整** (floor)，不足一天的金额记录在流水备注中
- **数据类型**: 使用 `decimal` 类型进行金额计算，避免浮点精度问题
- **流水记录**: 所有折算操作必须在 `user_bills` 中记录详细信息：
  - 旧套餐信息（plan_id, 剩余天数, 日均价）
  - 新套餐信息（plan_id, 日均价）
  - 折算结果（新增天数, 剩余金额）
- **审计要求**: 折算操作写入 `audit_logs`，保留完整计算过程

**影响范围**:
- `service/redemption_service.go`: `ConvertSubscription()` 方法
- `model/user_bills.go`: 新增 `conversion_metadata` 字段
- `controller/redemption.go`: 返回折算结果给前端

### 6.2 多订阅优先级决策

**问题**: 当用户拥有多个生效订阅时，如何确定使用顺序？

**决策**:
- **默认优先级**: 按到期时间升序排序（距离到期更近的优先使用）
  - 理由: 避免套餐到期浪费，优先消耗即将过期的额度
- **自定义调整**: 允许用户在"我的订阅"页面通过**拖拽**手动调整优先级
  - 前端: 拖拽交互，实时显示调整后顺序
  - 后端: 提供 `UpdateSubscriptionPriority` API，接收新的优先级顺序
  - 存储: `subscriptions.priority` 字段（**正整数**，值越小优先级越高）
- **优先级语义**:
  - priority 可以是**任意正整数**（不要求连续，如 1, 3, 10, 100 都合法）
  - 排序规则：priority ASC（主） → end_at ASC（副） → created_at ASC（兜底）
  - `NormalizePriorities()` 可将优先级整理为连续序列（1, 2, 3...），但非强制
- **动态插入**: 新订阅激活时，按 end_at 在现有 priority 序列中找到合适位置插入
  - 尊重用户已手动调整的 priority 顺序
  - 插入后后续订阅的 priority 依次 +1

**影响范围**:
- `service/subscription_priority_service.go`: 优先级排序、动态插入和更新
- `model/subscription.go`: 新增 `priority` 字段（默认值 1）
- Web 前端: "我的订阅"页面拖拽交互
- 计费链路: `PreConsumeQuota` 需按优先级遍历订阅

### 6.3 优惠券绑定规则决策

**问题**: 兑换码与优惠券的绑定关系如何管理？

**决策**:
- **绑定限制**:
  - 一个兑换码**仅能绑定一张优惠券**
  - 一张优惠券**可以被多个兑换码绑定**（批量发放场景）
- **绑定时机**:
  - **兑换前**: 允许管理员修改或重新绑定优惠券
  - **兑换后**: 绑定关系**锁定**，不允许变更
- **状态管理**:
  - 优惠券状态: `active` → `reserved`（绑定到兑换码） → `used`（兑换成功）
  - 若兑换失败或兑换码过期，优惠券状态回退为 `active`
- **数据存储方案**: 扩展 `coupons` 表，新增以下字段：
  - `bind_user_id`: 绑定的用户ID（可为空）
  - `bind_redemption_id`: 绑定的兑换码ID（可为空）
  - `bind_locked_at`: 绑定锁定时间（兑换后设置）
- **解绑规则**: 仅当 `bind_locked_at` 为空时允许解绑

**影响范围**:
- `model/coupon.go`: 新增绑定相关字段和方法
- `service/coupon_service.go`: `BindCouponToRedemption()`, `UnbindCoupon()`
- `service/redemption_service.go`: 兑换时自动消费绑定的优惠券
- 管理端: 兑换码管理页面，优惠券绑定界面

### 6.4 订阅取消通知决策

**问题**: 管理员取消订阅时，如何通知用户？

**决策**:
- **通知触发**: 管理员执行"取消订阅"操作时**必须触发**用户通知
- **通知渠道**: 遵循以下优先级
  1. 用户通知偏好设置（`user_settings.notification_preferences`）
  2. 系统默认通知配置（`system_settings.notification_channels`）
- **支持渠道**:
  - 站内通知（必须）
  - 邮件通知（若用户启用）
  - Webhook（若配置）
- **通知内容**: 包含以下信息
  - 订阅套餐名称
  - 取消原因（管理员必填）
  - 原有效期和取消时间
  - 退款说明（线下处理）
- **审计记录**:
  - `audit_logs` 记录取消操作（operator_id, reason, timestamp）
  - `user_bills` 记录退款流水（若有人工退款）

**影响范围**:
- `controller/subscription.go`: 管理员取消订阅 API
- `service/subscription_service.go`: `CancelSubscription()` 方法
- `service/notification_service.go`: 新增取消订阅通知模板
- 管理端: 取消订阅表单，需输入取消原因

### 6.5 自动余额兜底决策

**问题**: 当订阅额度不足时，是否自动切换到余额扣费？

**决策**:
- **配置层级**:
  - 系统级: `system_settings.subscription_auto_wallet_default` (布尔值)
  - 用户级: `users.auto_wallet_fallback` 或 `user_settings.auto_wallet_fallback`
- **优先级**: 用户设置 > 系统设置
- **默认值**:
  - **存量用户**: 迁移时默认设为 `false`（需通知用户）
  - **新用户**: 继承系统设置值
- **行为规则**:
  - `auto_wallet_fallback = true`: 订阅额度不足时自动扣余额，并记录流水
  - `auto_wallet_fallback = false`: 返回错误 `SUBSCRIPTION_LIMIT_REACHED`，不扣余额
- **审计要求**: 每次自动兜底扣费需在 `user_bills` 中标记来源为 `fallback`

**影响范围**:
- `model/user.go` 或 `model/user_setting.go`: 新增字段
- `service/quota.go`: `PreConsumeQuota()` 逻辑改造
- 用户设置页面: 新增"自动余额兜底"开关
- 迁移脚本: 设置存量用户默认值

### 6.6 令牌分组与订阅优先关系决策

**问题**: 令牌的"自动分组"与"订阅优先计费"如何协同？

**决策**:
- **字段扩展**: 保留 `tokens.auto_smart_group`（自动分组），新增 `tokens.subscription_preferred`（订阅优先计费）
  - `true`: 进入订阅扣费流程（订阅筛选不依赖令牌分组）
  - `false`: 跳过订阅扣费，直接使用余额或令牌分组
- **计费逻辑**:
  - 若令牌 `subscription_preferred = false`，即使用户有生效订阅，也跳过订阅扣费
  - 订阅筛选不依赖令牌分组，渠道匹配以订阅绑定分组为准
  - 令牌分组（含多分组优先级）仅用于余额路径
  - 通过 HTTP 响应头 `X-New-Api-Billing-Source` 和 `X-New-Api-Billing-Skip-Reason` 向调用方提示计费信息，不影响 OpenAI 格式兼容性
- **迁移策略**: 保留原有字段含义，新增订阅优先字段，不影响自动分组

**影响范围**:
- `model/token.go`: 字段扩展（新增 subscription_preferred）
- `service/quota.go`: 判定逻辑调整
- 迁移脚本: 新增字段 + Redis 缓存同步
- 用户界面: 新增订阅优先开关，保留自动分组开关

### 6.7 滚动窗口计算决策

**问题**: 订阅额度的周期限额如何计算和刷新？

**决策**:
- **窗口类型**: 支持两种窗口策略
  - `rolling`: **按需触发滚动窗口** - 窗口开始时间由用户首次使用触发
  - `fixed`/`natural`: 固定/自然窗口 - 按自然日/周/月边界

- **滚动窗口 (rolling) 核心规则**:
  1. **窗口开始时间** = 用户**首次实际使用计费**的时间（不是订阅开始时间）
  2. **窗口结束时间** = 窗口开始时间 + 周期时长
  3. **窗口结束后不会立即开始新窗口**
  4. **新窗口开始时间** = 上个窗口结束后，用户**下次首次使用计费**的时间
  5. 此逻辑循环往复

- **示例说明**:
  ```
  场景：用户 11:00 开通订阅，15:00 首次使用（5小时限额）

  第一个窗口：
  - window_start = 15:00（首次使用时间）
  - window_end = 20:00（15:00 + 5小时）
  - 15:00-20:00 期间的使用量累计到此窗口

  窗口结束后：
  - 20:00 窗口结束，但不会立即创建新窗口
  - 用户 21:00 再次使用时，创建新窗口

  第二个窗口：
  - window_start = 21:00（上个窗口结束后首次使用时间）
  - window_end = 02:00（次日，21:00 + 5小时）
  ```

- **固定/自然窗口 (fixed/natural) 规则**:
  - 窗口边界按自然时间边界计算
  - 日：UTC 00:00:00 - 23:59:59
  - 周：周一 00:00:00 - 周日 23:59:59
  - 月：每月1日 00:00:00 - 月末 23:59:59

- **策略选择建议**:
  | 周期 | 推荐策略 | 说明 |
  |------|----------|------|
  | `five_hours` | rolling | 滚动窗口，首次使用触发 |
  | `day` | fixed | 自然日，便于用户理解 |
  | `week` | rolling 或 fixed | 可根据业务选择 |
  | `month` | rolling 或 fixed | rolling 按 30 天计算 |

- **并发安全**: 使用数据库原子更新 `UPDATE ... WHERE used_quota + amount <= limit_quota` 确保不超扣

**影响范围**:
- `service/subscription_usage_service.go`: 窗口计算和刷新逻辑
- `model/subscription_usage.go`: 窗口字段定义
- 定时任务: 批量刷新过期窗口

### 6.8 其他关键决策

#### 6.8.1 订单快照
- 订单必须保存套餐和优惠券的**完整快照**（价格、限额、折扣等）
- 即使套餐或优惠券后续修改/删除，历史订单数据不受影响

#### 6.8.2 退款处理
- 系统**不提供自动退款**功能
- 退款由线下财务处理，但系统需支持写入人工退款流水
- 退款流水需标记 `refund_type = manual`，并记录操作员

#### 6.8.3 发票管理
- 系统不提供自动开票功能
- 需保留开票所需基础信息（订单号、金额、日期、用户信息）
- 发票由线下处理

#### 6.8.4 折算最小单位限制
**问题**: 当旧订阅剩余价值折算后不足新套餐 1 天的价格时，如何处理？

**决策**:
- **不允许进行折算**，直接返回错误提示用户端
- 错误码: `CONVERSION_INSUFFICIENT_VALUE`
- 用户可选择其他兑换选项（如 coexist、replace、extend）

**理由**:
- 避免用户产生"花费了套餐但只获得 0 天"的困惑
- 保持业务逻辑的清晰性和用户体验

#### 6.8.5 优惠券过期时机
**问题**: 用户优惠券 (`user_coupons`) 的过期判断逻辑是什么？

**决策**:
- 参考优惠券模板 (`coupons.end_time`) 作为过期时间
- 用户券的有效期 = 优惠券模板的 `start_time` 到 `end_time`
- 核销时校验 `current_time >= start_time && current_time <= end_time`

**理由**:
- 简化逻辑，统一由优惠券模板控制有效期
- 便于管理员批量管理优惠券的有效期

#### 6.8.6 并发领券频率限制
**问题**: 高并发场景下如何防止单用户频繁重试导致系统压力？

**决策**:
- **单用户领券频率限制**: 10次/分钟
- **乐观锁重试次数上限**: 10次
- 超过限制返回错误码 `COUPON_USER_LIMIT_REACHED` (HTTP 429)

**实现方式**:
- 使用 Redis 滑动窗口计数器记录用户领券频率
- Key: `coupon:claim:rate:{user_id}`
- TTL: 60秒

#### 6.8.7 订阅取消后的 usage 窗口处理
**问题**: 管理员取消订阅后，已创建的 `subscription_usages` 记录如何处理？

**决策**:
- **保留记录，用于审计**
- `subscription_usages` 记录不做任何修改或删除
- 订阅状态变为 `cancelled` 后，usage 记录自然失效（计费时会跳过非 active 订阅）

**理由**:
- 保持数据完整性，便于审计和问题排查
- 避免删除操作带来的数据不一致风险

#### 6.8.8 多订阅优先级冲突处理
**问题**: 当用户调整优先级时发生冲突 (HTTP 409)，如何处理？

**决策**:
- **自动规范化优先级**
- 服务端在保存时自动调用 `NormalizePriorities()` 将 priority 整理为连续序列（1, 2, 3...）
- 前端收到 409 后可自动重试或刷新订阅列表

**流程**:
1. 用户拖拽调整顺序
2. 前端发送批量更新请求
3. 服务端检测冲突后自动规范化
4. 返回规范化后的优先级顺序
5. 前端更新显示

#### 6.8.9 错误码定义

完整的错误码列表见 design.md 第7节，以下为关键错误码摘要：

**订阅相关**：
- `SUBSCRIPTION_LIMIT_REACHED`: 订阅额度已达上限
- `SUBSCRIPTION_NOT_FOUND`: 订阅不存在
- `SUBSCRIPTION_EXPIRED`: 订阅已过期
- `SUBSCRIPTION_INACTIVE`: 订阅未激活
- `SUBSCRIPTION_PRIORITY_CONFLICT`: 优先级冲突

**套餐相关**：
- `PLAN_NOT_FOUND`: 套餐不存在
- `PLAN_NOT_PUBLISHED`: 套餐未上架
- `PLAN_MODEL_WHITELIST_INVALID`: 模型白名单无效
- `PLAN_PRICE_INVALID`: 价格无效

**优惠券相关**：
- `COUPON_NOT_FOUND`: 优惠券不存在
- `COUPON_EXPIRED`: 优惠券已过期
- `COUPON_BINDING_LOCKED`: 优惠券已绑定无法修改
- `COUPON_RESERVED`: 优惠券已预留

**兑换码相关**：
- `REDEMPTION_INVALID`: 兑换码无效
- `REDEMPTION_USED`: 兑换码已使用
- `REDEMPTION_CONFLICT`: 兑换冲突（多套餐）

**订单和支付相关**：
- `ORDER_NOT_FOUND`: 订单不存在
- `INSUFFICIENT_BALANCE`: 余额不足
- `PAYMENT_FAILED`: 支付失败

**权限和验证相关**：
- `UNAUTHORIZED_OPERATION`: 无权操作
- `ADMIN_PERMISSION_REQUIRED`: 需要管理员权限
- `INVALID_REQUEST_PARAMS`: 请求参数无效

**窗口和额度相关**：
- `USAGE_WINDOW_EXPIRED`: 使用窗口已过期
- `USAGE_QUOTA_EXCEEDED`: 额度超限
- `CONCURRENT_UPDATE_CONFLICT`: 并发更新冲突

详细的错误码说明、HTTP状态码、触发场景和错误响应格式，请参考 design.md 第7节。
